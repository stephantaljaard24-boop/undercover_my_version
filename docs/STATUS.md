# Status

The claims pilot from `docs/SPEC.md` is built (`docs/PLAN.md`), and so is the agent's harness from `docs/HARNESS.md` (`docs/PLAN_HARNESS.md`): one run of the UnderCover Agent works the queue from a to-do list, hands each claim to a fresh helper, reads the wording and the claims manual by section and recovers from failures by itself.

## Run it

- `npm run dev` starts the backend on port 8000 and the dashboard on port 5173.
- `uv run -m agent` starts one run of the queue agent, which works every waiting claim. `uv run -m agent --limit 5` caps the run at five claims and leaves the rest waiting. `uv run -m agent CLM-1001` runs one claim with a fresh helper and no queue agent. It needs the backend running and `OPENROUTER_API_KEY` in `.env`; set `MODEL_NAME=openrouter/free` to use a free model.
- `uv run -m backend.seed` resets the SQLite database (`backend/undercover.db`, or `UNDERCOVER_DB`) to the 25 waiting claims in `data/`. `npm run seed` does the same on Supabase, by passing `.env`, and drops the whole `undercover` schema first. The backend loads the database by itself when its tables are missing. A database made before this build has the old tables, so reseed it once.
- `npm run check` runs every check.

## What's built

- `backend/`: FastAPI on SQLAlchemy Core, with SQLite by default and Supabase (Postgres, in the `undercover` schema) when `DATABASE_URL` is in its environment. `npm run dev` passes `.env`, and the tests never do. Amounts go over the API as dollar strings, such as `"420.00"`.
  - Inside: `main.py` only builds the app, `routes/` has the routes by resource (`claims`, `records`, `documents`, `runs`), `store.py` all the queries, `schema.py` the tables, `rules.py` the status, attempts and sign-off rules, `data.py` the files in `data/`, `db.py` the engine (at most 4 connections on Postgres) and resetting the schema. `backend/tests/openapi.json` is the saved API; a test fails when the live API differs, so a build that changes the API saves the new one on purpose.
  - `GET /api/claims` and `GET /api/claims/{claim_id}`: the queue and one claim in full
  - `GET /api/policies/{policy_id}` and `GET /api/customers/{customer_id}`: the policy, and the customer's name and earlier claims (no contact details)
  - `POST /api/claims/{claim_id}/start`: waiting to in progress
  - `GET` and `POST /api/claims/{claim_id}/steps`: what the agent did on a claim, oldest first
  - `POST /api/claims/{claim_id}/decision`: approve, decline or refer, with the payout rounded to the cent, an explanation and a policy section. A payout over the $1,000.00 limit (from `data/company.json`) leaves the claim `awaiting_sign_off`
  - `POST /api/claims/{claim_id}/payment`: records a payment of the approved payout. A payout over the limit is refused with a 403, so the payment stays blocked until a handler signs off. Other bad payments (not approved, wrong amount, already paid) get a 409
  - `POST /api/claims/{claim_id}/payout-calculation`: works out the payout on an approved claim from the benefit, the claim's lines and what others paid, with UnderCover's payout rules (`backend/payout.py`). The limit for a sign-off comes from `rules.approval_limit()`
  - `GET /api/instructions/queue` and `/claim`: the two sets of instructions, as plain text (`backend/instructions/`)
  - `POST /api/claims/{claim_id}/fail` takes a `reason`, records an `error` step and sends a claim in progress back to `waiting`, or to `needs_handler` ("Left for a handler") on its second failure. A decided claim can't be failed, decided again or paid twice
  - Runs: `POST /api/runs` (takes `claim_limit`), `PUT /api/runs/{run_id}/todos` (replaces the to-do list; each item is `todo`, `in_progress`, `done` or `left_for_handler`), `POST /api/runs/{run_id}/finish` (takes a `summary`) and `GET /api/runs/current` (the latest run, or null)
  - `GET /api/documents/{document}/contents` (`policy_wording` or `claims_manual`): the numbered sections, as text. `POST /api/claims/{claim_id}/reads` takes a `document` and a `section` number, records the read on the claim and returns the section's text. `GET /api/claims/{claim_id}/reads` lists what was read
- `agent/`: the queue agent and the claim helper, both LangChain's `create_agent` on the model in `MODEL_NAME`, or `deepseek/deepseek-v4.1-flash` with low reasoning effort by default. Two parts, and the harness imports nothing from UnderCover (a test checks it):
  - `harness/` runs any agent and knows nothing about claims: `model.py` (the model on OpenRouter), `agents.py` (`build_agent`: retries a failing model or tool, and cuts a runaway loop off after 40 model calls), `steps.py` (`run_agent` streams an agent, hands each tool call, tool result and reply to a function, and returns the last reply), `tools.py` (a tool whose refusal goes back to the model as text), `todos.py` (the `write_todos` tool, which saves the whole list through a function it is given) and `limits.py` (a run's cap, the lock that keeps work to one item at a time, and the check for items missed) and `tracing.py` (a claim's work goes to Langfuse in one session named for its thread, tagged with the claim id; nothing is sent without the Langfuse keys in `.env`).
  - `undercover/` is the business: `backend.py` (the `Backend` class, the only code that knows the backend's address, paths and status codes; it answers in small typed models, and a refusal raises `Refused`, which the tools hand to the model as text; `BACKEND_URL` points it at another backend), `tools.py` (the claim helper's eight tools: `get_claim`, `get_policy`, `get_customer`, `get_contents`, `read_section`, `calculate_payout`, `record_decision` and `pay_claim`), `claim_agent.py` and `queue_agent.py`.
  - `__main__.py` is the entry point and the only one: it reads the arguments and `.env`, connects a `Backend` and calls `work_claim` or `run_queue`. Nothing imports it.
  - `work_claim` (`claim_agent.py`) starts a claim, runs a fresh helper on it from a clean start with the claim instructions (`backend/instructions/claim.md`) and records every tool call, tool result and reply as a step. It never raises: a claim that fails or ends without a decision goes back to `waiting` (and to `needs_handler` on its second failure), and a claim that fails after being approved is paid once. A payout over $1,000 is approved but its payment is refused by the backend.
  - The queue agent (`queue_agent.py`, instructions in `backend/instructions/queue.md`) has four tools: `list_waiting_claims`, `write_todos` (replaces the run's to-do list, stored on the run in the backend), `work_claim` (hands one waiting claim to a fresh helper and returns one line; claims run one at a time, a claim that is not waiting is refused, and so is a claim past the run's cap) and `finish_run` (stores the summary, and is refused while a waiting claim is still within the cap). If it stops without finishing, its last reply becomes the summary.
  - `agent/tests/test_layout.py` fails if the harness imports UnderCover, if the product imports the entry point or `backend`, if any file is named `main`, `utils`, `helpers` or `runner` or runs over 300 lines, or if a backend path or `httpx` appears outside `undercover/backend.py`.
- `dashboard/`: React, Vite and TypeScript, in the brand's fonts and colors, light and dark from the system setting. Pages use hash routing (`#/`, `#/claims/CLM-1001`) and poll the backend every 3 seconds. Amounts are whole cents from the edge of `src/api.ts` on. Pages:
  - Queue: the current run's to-do list and summary (when there has been a run), a count for each of the five statuses (including "Left for a handler", in Raspberry) and a row for every claim
  - Claim (`#/claims/CLM-1001`): the claim in full, the agent's decision with its explanation and policy section, whether the payment is made or blocked for sign-off, the policy, the customer's earlier claims, the sections of the wording and the manual the agent read, and the agent's steps (failed attempts show as errors). It keeps polling (every 3 seconds while waiting, every 2 seconds after that) until the claim has a decision and the agent has given its final reply, because the agent pays and replies after it records the decision
  - Instructions (`#/instructions`): the instructions for running the queue and for working a claim, read only
- `e2e/`: Playwright tests. They start their own backend (port 8001, a database in the temp folder, seeded fresh each run) and dashboard (port 5174), and put claims into states through the API with made-up decisions.

Checked by hand on the default model (`deepseek/deepseek-v4.1-flash`) after the restructure and the new goal-style instructions, after a reseed: `uv run -m agent --limit 5` worked the five oldest claims on its own, with the same results as the first hand check. CLM-1001 was approved for $420.00 and paid, CLM-1008 ($2,240.00) and CLM-1011 ($1,150.00) were approved with their payments waiting for sign-off, CLM-1018 was referred and CLM-1010 was declined. The dashboard showed the to-do list filling in and being ticked off, then the summary. Each claim's page showed 12 to 17 sections read (8 to 10 with the old, longer instructions), and the other 20 claims stayed waiting. Nothing failed, so the retry and left-for-a-handler paths are covered by the tests only. The agent's accuracy has not been scored against `data/evals/`.
