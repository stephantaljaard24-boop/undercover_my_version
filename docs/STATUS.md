# Status

The claims pilot from `docs/SPEC.md` is built (`docs/PLAN.md`), and so is the agent's harness from `docs/HARNESS.md` (`docs/PLAN_HARNESS.md`): one run of the UnderCover Agent works the queue from a to-do list, hands each claim to a fresh helper, reads the wording and the claims manual by section and recovers from failures by itself.

## Run it

- `npm run dev` starts the backend on port 8000, the dashboard on port 5173 and the agent's service on port 8002, passing `.env` to the backend and the service so they reach Supabase. The service answers the backend's call after a handler signs off a claim, and picks that claim back up: `POST /api/claims/{claim_id}/resume` returns 202 at once and carries on in the background, only if the claim has a sign-off and its thread is paused.
- `uv run -m agent` starts one run of the queue agent, which works every waiting claim. It first carries on every claim left in progress (stopped by a crash or Ctrl-C, or signed off while the agent was away) from the last step its thread saved, and finishes a run that was stopped, with its cap, its to-do list and the claims it started. `uv run -m agent --limit 5` caps a new run at five claims and leaves the rest waiting. `uv run -m agent CLM-1001` carries on that claim if it is in progress and starts it if it is waiting, with no queue agent. It needs the backend running, and `OPENROUTER_API_KEY` and `DATABASE_URL` in `.env`; set `MODEL_NAME=openrouter/free` to use a free model.
- `uv run -m backend.seed` resets the SQLite database (`backend/undercover.db`, or `UNDERCOVER_DB`) to the 25 waiting claims in `data/`. `npm run seed` does the same on Supabase, by passing `.env`, and drops the whole `undercover` schema first. The backend loads the database by itself when its tables are missing. A database made before this build has the old tables, so reseed it once.
- `npm run check` runs every check.

## What's built

- `backend/`: FastAPI on SQLAlchemy Core, with SQLite by default and Supabase (Postgres, in the `undercover` schema) when `DATABASE_URL` is in its environment. `npm run dev` passes `.env`, and the tests never do. Amounts go over the API as dollar strings, such as `"420.00"`.
  - Inside: `main.py` only builds the app, `routes/` has the routes by resource (`claims`, `records`, `documents`, `runs`), `store.py` all the queries, `schema.py` the tables, `rules.py` the status, attempts and sign-off rules, `data.py` the files in `data/`, `db.py` the engine (at most 4 connections on Postgres) and resetting the schema. `backend/tests/openapi.json` is the saved API; a test fails when the live API differs, so a build that changes the API saves the new one on purpose.
  - `GET /api/claims` and `GET /api/claims/{claim_id}`: the queue and one claim in full
  - `GET /api/policies/{policy_id}` and `GET /api/customers/{customer_id}`: the policy, and the customer's name and earlier claims (no contact details)
  - `POST /api/claims/{claim_id}/start`: waiting to in progress, on a new thread of work. The claim carries its `thread_id`, such as `CLM-1003-ab12cd34`, which names the agent's saved progress and its Langfuse session
  - `GET` and `POST /api/claims/{claim_id}/steps`: what the agent did on a claim, oldest first
  - `POST /api/claims/{claim_id}/decision`: approve, decline or refer, with the payout rounded to the cent, an explanation and a policy section. A decline or referral is `decided`. An approval stays `in_progress` until it is paid, and a payout over the $1,000.00 limit (from `data/company.json`) is `awaiting_sign_off`. The same verdict and payout again counts as done and returns the claim; a different one gets 409
  - `POST /api/claims/{claim_id}/payment`: records a payment of the approved payout, which makes the claim `decided`. A payout over the limit is refused with a 403 until a handler has signed it off. Paying the paid amount again returns the claim, and any other bad payment (not approved, wrong amount) gets 409. The payment shows who signed off and when
  - `POST /api/claims/{claim_id}/sign-off` takes a `handler_id`: a claim `awaiting_sign_off` becomes `in_progress`, the sign-off is saved with the handler's name and the time, and after the response the backend tells the agent's service (`UNDERCOVER_AGENT`, default `http://127.0.0.1:8002`) with `POST /api/claims/{claim_id}/resume`. The sign-off stands if the agent can't be reached. A second sign-off returns the claim unchanged. `GET /api/handlers` lists the handlers (without their emails)
  - `POST /api/claims/{claim_id}/payout-calculation`: works out the payout on an approved claim from the benefit, the claim's lines and what others paid, with UnderCover's payout rules (`backend/payout.py`). The limit for a sign-off comes from `rules.approval_limit()`
  - `GET /api/instructions/queue` and `/claim`: the two sets of instructions, as plain text (`backend/instructions/`)
  - `POST /api/claims/{claim_id}/fail` takes a `reason`, records an `error` step and sends a claim in progress back to `waiting`, or to `needs_handler` ("Left for a handler") on its second failure. A decided claim can't be failed, decided again or paid twice. A claim with a decision is refused (409): it stays in progress and the agent carries it on
  - Runs: `POST /api/runs` (takes `claim_limit`), `PUT /api/runs/{run_id}/todos` (replaces the to-do list; each item is `todo`, `in_progress`, `done` or `left_for_handler`), `POST /api/runs/{run_id}/finish` (takes a `summary`) and `GET /api/runs/current` (the latest run, or null). `POST /api/runs/{run_id}/claims` records a claim the run started, and a run lists them as `started`
  - `GET /api/documents/{document}/contents` (`policy_wording` or `claims_manual`): the numbered sections, as text. `POST /api/claims/{claim_id}/reads` takes a `document` and a `section` number, records the read on the claim and returns the section's text. `GET /api/claims/{claim_id}/reads` lists what was read
- `agent/`: the queue agent on LangChain's `create_agent`, and the claim agent as a hand-written LangGraph graph, both on the model in `MODEL_NAME` (or `deepseek/deepseek-v4.1-flash` with low reasoning effort by default). The harness imports nothing from UnderCover (a test checks it):
  - `harness/` runs any agent or graph and knows nothing about claims: `model.py` (the model on OpenRouter), `agents.py` (`build_agent`: retries a failing model or tool, and cuts a runaway loop off after 40 model calls), `graphs.py` (what a hand-written graph needs in place of that middleware: a retry policy for its nodes and a count that stops the model being called more than 30 times), `checkpoints.py` (a Postgres saver for a graph's progress, opened for one piece of work and closed), `steps.py` (`run_graph` streams an agent or graph, hands each tool call, tool result and reply to a function, and says if the graph paused), `tools.py` (a tool whose refusal goes back to the model as text), `todos.py` (the `write_todos` tool), `limits.py` (a run's cap, the lock that keeps work to one item at a time, and the check for items missed) and `tracing.py` (a claim's work goes to Langfuse in one session named for its thread, tagged with the claim id; nothing is sent without the Langfuse keys in `.env`).
  - `undercover/` is the business: `backend.py` (the `Backend` class, the only code that knows the backend's address, paths and status codes; it answers in small typed models, and a refusal raises `Refused`, which the tools hand to the model as text; `BACKEND_URL` points it at another backend), `tools.py` (the claim agent's six tools: `get_claim`, `get_policy`, `get_customer`, `get_contents`, `read_section` and `calculate_payout`), `claim_graph.py`, `claim_agent.py`, `checkpoints.py` (the saver on the `undercover` schema of `DATABASE_URL`) and `queue_agent.py`.
  - `__main__.py` and `service.py` are the entry points, and nothing imports either. `__main__.py` reads the arguments and `.env`, connects a `Backend` and calls `pick_up` on a named claim or `run_queue`. `service.py` is a small FastAPI app with a health check and the resume route.
  - The claim graph (`claim_graph.py`) has an `agent` node and a `tools` node that loop until the model stops asking for tools, then `decide` (the model gives a structured decision), `record` (records it in the backend, which says whether it needs a sign-off), `sign_off` (`interrupt()`, which pauses the graph until a handler signs off) and `pay` (pays the recorded payout through the backend). The graph never compares a payout with the limit: it asks the backend. A decline or referral ends after `record`. Its state is saved in Postgres after every step (`durability="sync"`), on the claim's thread, which is the `thread_id` the backend gave when the claim started. The instructions are `backend/instructions/claim.md`.
  - `ClaimAgent` (`claim_agent.py`) works claims. `work_claim` starts a claim on a new thread, runs the graph, and records every tool call, tool result and reply as a step. `carry_on` takes a claim in progress from the last step its thread saved, without a new attempt: a thread that stopped partway is run on, and one paused for a sign-off is resumed once the backend has it. `pick_up` carries on a claim in progress and starts any other. An error before a decision sends the claim back to `waiting` (to `needs_handler` on its second failure) and the next try starts a new thread. An error after the decision leaves the claim in progress on its thread, and the next run carries it on. A payout over $1,000 pauses the graph until a handler signs off.
  - `run_queue` first carries on the claims left in progress, then carries on the latest run if it is not finished (a fresh queue agent is told its cap, the claims it started and its to-do list) or starts a new one. The `work_claim` tool records each claim it starts on the run in the backend. The queue agent (`queue_agent.py`, instructions in `backend/instructions/queue.md`) has four tools: `list_waiting_claims`, `write_todos` (replaces the run's to-do list, stored on the run in the backend), `work_claim` (hands one waiting claim to a `ClaimAgent` and returns one line; claims run one at a time, a claim that is not waiting is refused, and so is a claim past the run's cap) and `finish_run` (stores the summary, and is refused while a waiting claim is still within the cap). If it stops without finishing, its last reply becomes the summary.
  - `uv run -m agent` needs `DATABASE_URL` in `.env`, because the claim graph saves its progress there.
  - `agent/tests/test_layout.py` fails if the harness imports UnderCover, if the product imports the entry point or `backend`, if any file is named `main`, `utils`, `helpers` or `runner` or runs over 300 lines, or if a backend path or `httpx` appears outside `undercover/backend.py`.
- `dashboard/`: React, Vite and TypeScript, in the brand's fonts and colors, light and dark from the system setting. Pages use hash routing (`#/`, `#/claims/CLM-1001`) and poll the backend every 3 seconds. Amounts are whole cents from the edge of `src/api.ts` on. Pages:
  - Queue: the current run's to-do list and summary (when there has been a run), a count for each of the five statuses (including "Left for a handler", in Raspberry) and a row for every claim
  - Claim (`#/claims/CLM-1001`): the claim in full, the agent's decision with its explanation and policy section, whether the payment is made or blocked for sign-off (with a choice of handler and a Sign off button while it is blocked, and who signed off and when once it has), the policy, the customer's earlier claims, the sections of the wording and the manual the agent read, and the agent's steps (failed attempts show as errors). It keeps polling (every 3 seconds while waiting or waiting for sign-off, every 2 seconds while in progress) until the claim is decided or left for a handler, because the agent pays an approval after it records the decision and after a sign-off
  - Instructions (`#/instructions`): the instructions for running the queue and for working a claim, read only
- `e2e/`: Playwright tests. They start their own backend (port 8001, a database in the temp folder, seeded fresh each run) and dashboard (port 5174), and put claims into states through the API with made-up decisions.

Checked by hand on the default model (`deepseek/deepseek-v4.1-flash`) after the restructure and the new goal-style instructions, after a reseed: `uv run -m agent --limit 5` worked the five oldest claims on its own, with the same results as the first hand check. CLM-1001 was approved for $420.00 and paid, CLM-1008 ($2,240.00) and CLM-1011 ($1,150.00) were approved with their payments waiting for sign-off, CLM-1018 was referred and CLM-1010 was declined. The dashboard showed the to-do list filling in and being ticked off, then the summary. Each claim's page showed 12 to 17 sections read (8 to 10 with the old, longer instructions), and the other 20 claims stayed waiting. Nothing failed, so the retry and left-for-a-handler paths are covered by the tests only. The agent's accuracy has not been scored against `data/evals/`.

Left for later, as the spec says: sign-in (a handler picks their own name to sign off), rejecting a held payout, real payments and messages to customers, and scoring the agent against `data/evals/`.
