# Tech stack

- `backend/`: FastAPI on SQLAlchemy Core, in layers: `main.py` builds the app, `routes/` has the routes by resource, `rules.py` the status, sign-off, repeat and payment rules, `payout.py` the payout rules, `store.py` all the queries, `schema.py` the tables, `db.py` the engine. The database is SQLite, or Supabase (Postgres, session pooler) when `DATABASE_URL` is in the backend's environment. Every table is in a schema of its own, `undercover`, set on the Postgres connection so each query is written once for both databases, and the backend keeps at most 4 connections. `npm run dev` passes `.env` to the backend, and the tests never do. The backend also serves the wording and the manual by section, keeps each run and its to-do list, and tells the agent's service when a handler signs off a claim (`agent_client.py`, address in `UNDERCOVER_AGENT`, default `http://127.0.0.1:8002`). Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount, and a decision or a payment that repeats one already recorded counts as done.
- `agent/`: LangChain on OpenRouter, and LangGraph, with no other agent framework. A queue agent (LangChain's `create_agent`) runs the whole queue from a to-do list and hands each claim to the claim agent, which is a hand-written LangGraph graph that works it from a clean start. Its progress is saved after every step in Supabase, in the same `undercover` schema, with LangGraph's Postgres checkpointer (synchronous, `durability="sync"`), and it waits for a sign-off with `interrupt()`. Langfuse traces each claim's work in one session named for the claim's thread. Two entry points: the command line, which runs the queue (with an optional cap on claims) or one claim by its id, and carries on whatever was left; and a small web service, started by `npm run dev` beside the backend and the dashboard, which the backend calls after a sign-off. It uses `deepseek/deepseek-v4.1-flash` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`. Its layout: `harness/` runs any agent or graph (the model, the middleware, a graph's retries and call limit, running one and streaming its steps, saving its progress, tracing it, the to-do list tool, a run's cap and lock) and knows nothing about claims; `undercover/` is the business (the one client for the backend, the claim tools, the claim graph, the claim agent and the queue agent); `__main__.py` and `service.py` are the entry points. Imports point one way, entry point to `undercover` to `harness`, and a test checks it. The agent reaches claims, the wording, the manual and its instructions only through the backend's API, in `undercover/backend.py` and nowhere else.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests. They run their own backend and a stand-in for the agent's service.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. The OpenRouter key is `OPENROUTER_API_KEY` in `.env`, the Supabase session pooler connection string is `DATABASE_URL`, and the Langfuse keys are `LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`.
